# 正常、恶意与待核实样本的质量要求

生成或复核训练记录前阅读。目标是让模型依据实际可见的请求、关系和授权状态判断，控制正常邮件误报，并如实保留信息不足的情况。二分类字段继续使用 [schema.md](schema.md)；本页的复核队列是独立工作流。

## 1. 先固定观察范围

在批次计划和交付说明中写明下列输入范围与观察时点，无需为此新增训练记录必填字段。不同范围可以分别成批，评估时分开统计。

| 输入范围 | 可以提供的内容 | 不可用来补答案的内容 |
|---|---|---|
| 仅当前邮件 | 发件人正文、主题、个人标识脱敏后的邮件头、原始邮件链接及现有契约允许的附件元数据 | 作者编写的业务背景、过去未提供的邮件、未约定的附件正文、后来访问网页的结果 |
| 邮件线程 | 当前邮件与该时点确实可获得的先前往来；改编线程须内部一致并披露 | 未来回复、事后询问真实供应商得到的答案、调查结论 |
| 邮件及业务背景 | 上述内容加实际检测系统会提供的订单、授权、账号状态或组织流程 | 只有生成器知道的真实身份、隐藏账户归属、“这是钓鱼”等判断 |

生成任务未指定范围时，按 [随机选题与形态](topic-selection.md) 在规划阶段抽选可成立的单封、往来或含实际背景形态，并披露各自范围；单封邮件使用空历史，可完全没有业务背景。审核已有邮件时从实际提供的材料出发；已有语料沿用实际输入约定。需要线程或业务背景才能判断的题材应明确选择相应范围，不能只为凑出二分类答案添加背景或随机删去必要证据。当前 v2 的跨境／美元记录要求 `input.business_context`，这类记录须归入含业务背景的范围；用户要求保持仅当前邮件且不扩展契约时，报告该题材的契约冲突和未验收数量，不静默附加背景、改币种或删除必填字段。

现有 v2 的附件只有名称与类型。任务确需附件可读文本时，先明确扩展字段、内容提取来源、脱敏、证据路径及校验，再用于单独约定的输入范围；脚本允许额外键不代表它已验证附件正文。扩展前，不把附件摘要塞进发件人正文或借 `business_context` 隐式加入。

新记录保留已取得的邮件 URL 原值和按钮文字与目标的对应关系，适用于正常与恶意两类；不再统一替换为 `[URL_n]`。个人姓名、邮箱、用户名仍按 [数据边界](realism-details.md) 脱敏；URL 含这些私人标识时只替换对应片段并记录处理，保留其余可用结构。来源报告的网址留在 provenance，不能拿来冒充报告中未披露的邮件跳转目标。URL 作为训练文本保存，不自动访问；判断历史案件时区分当时披露的用途与现在的状态。

保留 URL 不等于获得了网页内容、域名归属或授权结果。不能仅因 HTTPS、短链、长查询串、域名陌生或表面不一致断言正常或恶意；只用当前输入可支持的区别。邮件头的额外技术特征仍需约定字段及校验，不能凭空恢复。旧记录中的链接占位可以继续读取，但两个不同目标都变成 `[URL_1]` 时差异已丢失，不倒推原值；“正常链接”和“钓鱼链接”也不能作为替代文字。任何清洗后都重查可判性，完全相同的输入不能承载相反标签。

保留案件中的观察阶段。正文仅有安全确认按钮时，不能为使其显得恶意而普遍改成“回复密码”。阶段或渠道改编的例外用于任务明确要求比较不同渠道或观察时点的研究：行为本身须有材料支持，改动、研究目的和分布单独说明与计数。“让标签明确”本身不构成这一例外。常规覆盖中保留原有引导形态，当前证据不足的条目进入复核队列。后续页面、通话或授权过程只有在任务明确包含该观察阶段时才可建模。

## 2. 三种审核结果与业务差错

| 审核结果 | 进入条件 | 处理 |
|---|---|---|
| 正常 `benign` | 有依据的任务、请求和可见上下文相符，证据支持其正常性质 | 纳入二分类语料；不能仅因为没看到明显恶意就判正常 |
| 恶意 `malicious` | 当前输入有证据支持欺骗性索取、越权授权、资金转移或流程篡改等行为 | 纳入二分类语料；证据引用具体动作及所需基准 |
| 待核实 | 当前信息无法区分合理请求与威胁，或来源、通信层次存在未解决问题 | 进入独立复核队列，不硬贴任一标签 |

业务异常与恶意分别判断。漏附件、填错金额、催办、退信、账户异常登录、未经确认的变更都不自动证明发件邮件恶意。真实服务发来的账号入侵警报，其报告的事件可能危险，警报邮件本身仍可能正常。垃圾邮件、营销邮件、系统判定的可疑邮件也不自动等同于诈骗；只有用户明确另设任务时才改变标签定义。

对授权或流程的冲突，区分已批准、待申请、申请例外与隐瞒实际变更。申请新账户并等待复核可以正常；明确把未获授权的收款对象或操作冒充为已批准安排，才可能形成相应威胁证据。单一差异、陌生服务名和发件人自称已获批准都不足以替代核对。

BPC 还应检查货物去向、收货／售后状态、权益归属、返利依据、验收里程碑、授信和理赔记录，具体参照 [八类流程场景](bpc-scenarios.md)。基准、改动和后果须相互对应：新地址不自动是盗货，部分验收不自动是虚假验收，多次赔付不自动是骗赔，允许的转赠也不等于权益盗用。不要因新增场景名称而跳过正常例外和未知授权的核对。

## 3. 分离原邮件与外部裁定

先确定分类对象是原始来信、转发者的举报邮件，还是安全系统发出的通知。按对象保留发送者真正写下的内容，并在来源或处理说明中记录提取边界。

- 邮箱客户端或网关附加的“该邮件可能存在恶意内容”“检测结果：垃圾邮件”、风险评分和隔离标签属于外部裁定。默认原邮件语义识别任务将它们移出 `input`，在脱敏后的来源／处理说明中保留其存在与移除原因；不能把它们当独立真值。
- 正常隔离摘要可能在正文列出一封邮件的垃圾分类。这时摘要本身是分类对象，不能机械删除其中的业务内容，也不能把被摘要邮件的标签当作整封摘要的标签。
- 举报、咨询或安全培训邮件可能引用恶意请求。按发件人的实际言语行为判定，区分“请执行这个请求”和“这封邮件要求我执行，是否可信”。不要因引用里出现密码、转账或恶意话术直接判定外层邮件恶意。
- 确需把网关结论作为特征的任务，应单独约定输入与真值来源，独立评估；不得用同一检测器的结论同时充当输入提示和标准答案。
- 来源层次不明时保留待核实状态，不能用关键词正则删掉所有安全警告。改写、拆分或清洗后重新定位 evidence 与 provenance 中的精确引用。
- 从安全平台的截图、复制文本或详情导出提取时，将报告的检查覆盖、截断、外链图片未解析、缺少 Received、SMTP 会话、链接计数及观察分数保留在处理说明中。默认语义输入只保留确认属于原信的材料。页面出现“正常”“safe”“待定”或低分时，仍按实际证据复核。[平台详情处理](survey-and-mail-inspection.md#2-从平台详情提取原信)

## 4. 建立同场景对照

用户要求训练正常／恶意区别或评估混合语料时，覆盖普通正常、容易误报的正常、明显恶意、需上下文判断的恶意，并保留待核实条目供复核。按实际需求安排比例，记录分布；不把均衡训练比例宣称为真实收件箱比例。用户指定只生成某类时遵循其范围，说明未检验的类别。

| 场景 | 正常难例 | 有证据才成立的威胁区别或待核实边界 |
|---|---|---|
| 账号安全通知 | 用户本人操作后收到带按钮、期限或验证码的提醒；真实服务通知新设备登录 | 凭证被要求交给他人、授权对象与本人操作不符；仅有按钮且目标与触发状态未知时待核实 |
| 人事资料／福利 | 合理核对岗位、联系信息或实际发放所需资料，存在催办和补件 | 索取与任务无关的密码、认证秘密或不必要的资料；字段范围未知时进一步核实 |
| 品牌／商家对客抽奖 | 有依据的活动邀请、中奖通知、领取确认或寄送安排，可使用醒目标题、期限和必要收件信息 | 首次收到、不记得报名、品牌名、单有按钮或存在费用不单独定性；结合具体请求判断索密或与可见活动规则冲突的索款，条件不足时待核实 |
| 健康福利／有奖问卷 | 已知主办方邀请自愿反馈，说明奖励条件和经核对的问卷入口，可用第三方问卷服务和 HTML 按钮 | 问卷按钮、云存储主机、缺失远程图片或检查评分单独不足以定性；观察阶段有可见的欺骗、越权索密或与规则冲突的索费才支持威胁标签 |
| 国补发放／退税 | 有依据的资格、补件、审核、核销或退付进度通知，可为完整的单封邮件 | 区分立减与现金拨付、审核与到账；有证据的索取认证秘密、额外预付或偏离已知发放路径才形成威胁依据，不能只凭主题或语气判定 |
| 收款信息变更 | 合作方提出变更，按已有授权完成核验或明确等待审核 | 改付要求与既有义务冲突、把未经批准的路径冒充已批准路径、隐瞒实质变更 |
| 发票／金额更正 | 更正重复、误填、版本错误，说明原因并等待确认 | 有可见证据的重复索款、篡改凭据或隐瞒退款；单次金额不符不足以定性 |
| 收货／售后／交付／权益 | 已解决后结案、经本人确认的改址、正式提货委托、符合规则的转赠或补发 | 虚报未完成状态、向未授权对象交付或核销；对照实际订单、授权及状态，不能只凭“改地址／代领／撤销”判断 |
| 返利／验收／授信／理赔 | 合理跨期扣减、分段验收、等待审批的额度调整、适用责任范围内的补赔 | 有依据的隐瞒退款、虚报验收、冒称已获放货授权或重复核销；需引用具体结算／授权基准与改动，规则未知时复核 |
| 紧急业务请求 | 有截止期的补件、付款、会议或服务续期 | 催促结合具体欺骗或越权行为判断，语气急迫本身不决定标签 |
| 邮件举报／隔离摘要 | 转发可疑邮件询问管理员，或正常系统列出隔离事项 | 区分外层请求与被引用内容；无法分辨层次时不强行定标签 |

正常样本应有日常摩擦和合理的不完整信息，不必处处附安全承诺或验证教程。恶意样本保留来源支持的机制，允许措辞专业、简短或无链接；不人为往每封中加入“保密”“不要核验”来确保恶意明显。

两类的称谓、格式、长度、标点、品牌、链接呈现、期限和附件形式应有交集。正常邮件也保留真实入口，恶意邮件不强制带链接。检查去掉关键语义后，是否仍能仅凭模板或固定域名集合认出标签；若可以，调整选材或表达分布，并按相关来源／活动分组评估。

同场景对照不要求同属 `pair_id`。现有最小／场景对均为两条、相反二分类标签，且历史与业务背景相同。正常／恶意／待核实的三方评审，或需要改变历史授权状态的对照，使用独立记录，通过 `source_group`、`template_family_id` 或 `thread_family_id` 记录关联；不能破坏原配对契约。待核实项不计为第三个配对成员。

## 5. 复核队列的交付约定

仅在实际生成或审核语料任务产生待核实项时，单独交付 `review_queue.json`（UTF-8 数组）；仅维护 Skill 时不创建该队列或训练样本。它不是 schema 2.0 训练数组，不合并到 `corpus.json`，也不传给 `validate_records.py`。

| 字段 | 含义 |
|---|---|
| `id` | 不编码预期标签的候选标识 |
| `input` | 个人标识已脱敏、已知邮件链接保留原值的可见材料。保留实际提供的字段；缺发件人、链接目标等时不编造内容补齐训练结构 |
| `review.status` | 固定为 `needs_review`，表示工作流状态，不是模型类别 |
| `review.reason` | 具体说明为什么当前不能可靠定类；不得只写“可疑” |
| `review.missing_information` | 字符串数组，列出需要补足的依据或需解决的矛盾 |
| `review.input_scope` | 本次判断实际使用的输入范围与观察时点 |
| `provenance` | 已有的脱敏来源、外部裁定与处理说明；未检索时不得伪造检索日志或 verified 声明 |
| `source_group`／`template_family_id`／`thread_family_id` | 已知关联时保留，用于后续划分去重 |

队列条目不写 `target.label`，不创建占位答案、不把未知当成 `benign`。复核者获得依据后重新审读，生成完整 v2 记录、绑定来源与证据并通过正式校验，才可纳入训练集。报告已验收数量及各标签数量，并另报待核实数量；不能将待核实条目充作用户要求的有效记录数。原因可能多项并存，例如链接目标缺失、缺少授权状态、脱敏丢失关键差异、外部告警来源不明、来源不足或规则冲突。

## 6. 把要求落实为验收

1. **结构校验。** 对正式训练数组运行现有脚本，核对来源引用、数量和格式。新批次使用 `--require-raw-urls` 检查未遗留 `[URL_n]`；不要求每封邮件包含链接，也不证明所留 URL 真实。脚本不会证明邮件自然、标签正确、网关告警已分离或范围约定被遵守。
2. **逐条盲审。** 审读者只看该任务允许的 `input`，判断正常、恶意或待核实并指出依据；随后对照原标注与来源。单封邮件另查正文自身是否完整、语义连贯、标题与请求一致，不能靠元数据补足阅读所需信息。分歧须核对证据，不能由生成器的预设标签裁决。可用独立 AI 评审协助，仍须披露评审方法和局限。
3. **对照复核。** 检查关键语义差别是否足以支持标签变化，以及普通更正、正常认证和安全通知是否被误报。不可判定性与高难度分别记录，不能把缺信息包装成 `hard`。
4. **防止跨集合泄漏。** 同来源案件、线程、模板家族、配对以及改写版本按关联形成整体分组，再划分训练／验证／测试。复核队列转正后仍继承其分组；存在交叉关联时不能只按单个 ID 隔离。
5. **按场景报告结果。** 未训练检测器时只报告抽检量、分歧及返修原因；实际评估检测器后再报告正常误报率、恶意召回率、待核实／拒判比例及样本量。按输入范围、系统／人工邮件及场景分开看，不能用单一准确率或几条示例推断真实部署效果。

Skill 维护时可用文档审查和不落盘的场景决策走查检验这些规则。用户限定“只负责 Skill”时，不执行语料生成、追加或重标注。
