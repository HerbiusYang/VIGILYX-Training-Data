# 邮件真实感与脱敏规范

基于可核验的公开安全事件或通信材料，模拟收件人看到的邮件。人工往来体现关系与沟通过程，系统通知体现通知对象、触发事项与操作／状态；二者均应自然、正式得体、逻辑连贯。事后核验、来源和解释放入元数据。先核实材料，再处理表达和脱敏。[来源与改编指引](source-grounding.md) · [场景指引](scenario-playbook.md) · [系统通知](system-notices.md)

## 默认地区、金额和语气

以中国大陆收件场景为主，默认写中文邮件、人民币金额。美元需要有跨境采购、出口收款、境外服务续费或其他有依据的美元外币业务背景。境内美元业务仍按境内处理。外币和业务地区依实际依据填写。

地区和币种放进元数据：`business_region: CN`；`transaction_scope` 区分 `domestic` 与 `cross_border`；`currencies` 只列本例实际涉及的 `CNY`／`USD`。跨境例用 `cross_border_context` 说明中国一方是谁、与哪里发生什么交易及所用币种；境内美元例保持 `domestic`，另用 `currency_context` 交代真实适用的外币业务和使用美元的原因。两种情况都要在正文给读者足够的业务背景，不能只靠元数据补理由。代码用于元数据，正文写“32,480元”“169.50元”“2,450美元”，不要写成代码在前、数字在后的财务接口格式。

上述金额仅示意格式，不是可借用的个案事实。正文可自然说明应付、已付和剩余金额。引用真实记录时保持原金额、币种和精度；改编金额时在 `provenance.grounding.adaptations` 明确记录并保证算术一致，不能说成来源原值。不要虚构真实汇率、擅自把美元换算成人民币或将两种币种直接相加。公开账户的户名、账号、开户行及行号是原始资料，绝不能随金额排版一起改写、去空格或截断。

### 按关系和用途选择措辞

新编人工邮件采用自然、完整、符合身份与用途的中文表达，使用完整句子、明确指代和适当敬语。正式业务通知保持得体，消费者活动邮件可采用强吸引力的宣传表达，具体见 [独立邮件与表达风格](#独立邮件与表达风格)。系统通知可采用简短界面式文案和服务署名，按其目的保留完整信息。`register` 记录实际关系和文种，不要求一律选择 `formal_notice`。真实原件保留原有语气；不能为统一风格虚构官方身份或改变原材料性质。

| `register` | 适用关系和写法 |
|---|---|
| `daily_business` | 同事、熟悉的供应商和日常跟进。称呼与关系匹配，简要承接此前事项，清楚提出请求，例如“关于昨天提交的核对结果，还有一项需要请您确认”。保持礼貌和完整句意；已有熟悉往来时可更简洁。 |
| `customer_service` | 品牌／商家对个人消费者、客服对客户或首次联系的外部对象。用“您好”“您”等适当敬语，说明来意或所回复的咨询，再说明活动、服务、所需材料与下一步；无需虚构一封客户先发来的咨询。 |
| `formal_notice` | 正式通知、合同函件及系统自动通知。称谓、结构和署名与文种相称；短系统卡片可用通知标题、用户称呼和服务页脚，无需个人礼貌收尾。正式语气不证明官方身份、政策或权威。 |

上面的短语仅示意语气。保留必要术语，并说明具体对象及状态。称呼、礼貌用语和落款要自然变化，不将所有邮件写成同一套开场和结尾。明确用户要求正式时遵循其要求；已有回复可以简洁，仍要完整承接前文。

### 面向收件人的用词与渠道检查

新编或润色中文邮件时，使用收件人实际会说的邮件语言。`thread`、`history`、上下文、样本、标签等生成或数据组织概念，不应因作者看过字段定义就进入普通业务正文。谈邮件沟通时不使用“在这个线程回你”“本线程继续跟进”“拉入邮件线程”，按真实动作写“回复这封邮件”“通过邮件告知你”“抄送相关同事”等；保持原有收件范围和回复关系，不能在改词时擅自增加抄送人或改走其他渠道。

| 检查项 | 容易失真的表达或关系 | 成文处理 |
|---|---|---|
| 邮件、聊天与工单 | 把邮件叫“线程／会话”，把工单处理写成“在邮件里关闭”，或无聊天背景却说“私信我” | 区分沟通渠道和业务对象：回复邮件、在工单中更新、通过已有聊天渠道联系；只有已知操作渠道才写具体入口 |
| 动作及对象 | “接续工单”“回传结果”“推进闭环”等说法掩盖实际动作 | 按意思写“继续处理原工单”“通过邮件告知处理结果”“核对完成后更新工单状态”等；这些是可选表达，不是逐词替换表，不能补出原文没有的动作或承诺 |
| 称谓及人称 | 同一收件人无缘由地切换“你／您”，把同事称“贵司”，或直接对客户写“请客户提供” | 按真实关系统一称谓，明确“我／我们／您／对方”指谁；角色名和敬语自然搭配，不用过度公文化表达代替清楚说明 |
| 状态的准确程度 | 将“已受理”写成“已批准”，把“限制发送”扩大为“无法登录”，把“已提交付款”写成“已经到账” | 保留已知状态、限制范围和未决结果；不为显得正式而改变完成程度、权限或业务含义 |
| 回复与通知方式 | 一面要求“回复本邮件”，一面写“系统自动发送，请勿回复”；或变更渠道却仍称“在这里回复” | 当前要求与实际可用回复方式一致；自动通知引用其他邮件的回复要求时保留清楚层次，不能凭空补一个客服入口解决矛盾 |
| 引用与附件 | 没有明确对象却写“上面那个／如下附件／见历史”，新增“再次提醒”却无相应前情 | 在允许输入内准确指向此前邮件、附件名称或本次事项；已有对象就说明，缺少对象就删去无依据的承接，不编造历史或附件 |

这些检查适用于新编主题、正文、签名及改编历史，也适用于两类标签。交付前单独通读一遍：收件人能否自然理解谁在何处处理什么、现在到哪一步、接下来如何回复。发现问题时重写相关句子，再核对事实、请求、收件关系及 evidence 精确引用保持一致。

不用全局禁词或机械替换：讨论 CPU 线程、数据库回写、网络链路或真实产品“会话视图”时保留准确术语；英文邮件的自然 `email thread` 用法、内部 `thread_family_id` 和真实原文引用也不受中文业务措辞规则误伤。`redacted-source` 原文不能无声明地润色；修改措辞须按已有契约归为 `source-adapted`。自动结构校验不证明这项语义审读已经完成。

## 1. 真实依据与情节改编

- 按指定主题先明确要让收件人识别的动作，再实际检索支持这一动作的威胁机制和必要的正常流程。分别记录真实机构、适用规则、原案事实和新邮件改编。
- 允许基于上述依据改编交易金额、个案时间、业务阶段、角色分工、对话及内部复核安排；逐项记入 `provenance.grounding.adaptations`，不把新情节说成真实往来或来源事实。该许可不包含凭空设计真实品牌活动，或改变已核实活动的奖品、资格、规则与适用期次。内部安排只作为本例明确设定，不冒称真实银行、平台或公司的现行制度。
- 具名机构、企业户名、账号、开户行、支行、机构／银行代码及公开政策必须真实且可核实，不随情节改写。覆盖正文、历史、签名和附件；不得编真实机构专属部门、员工身份或政策以补可信度。
- 上述核实针对现实实体和制度断言。用户原件中未核实的服务显示文字可作为发件人声称保留并记录其未知状态，不为它编造机构来源，也不把它列成已验证实体。生成时可使用通用系统角色，不能冒称一个未核实的产品真实存在。
- 来源匿名的案例不能替换成另一个真实公司并宣称还原；公开账户不能补进无关原案。独立改编使用真实机构时，另核业务和账户用途，并在元数据说明新情节，不能暗示该机构真实涉案或实施恶意行为。
- 官方帮助可支持服务规则，反诈说明可支持风险机制，案件通报支持其明示的事件；均不自动证明某封新邮件真实发出。可据此明确改编，但不能声称改写的是未公开的邮件原文，或由 App 功能推断机构存在某种官方邮件流程。
- 分别记录发布日期、事件日期、访问日期和改编时间，不把无日期旧文的“近期”解释成当前真实案件。缺乏业务／风险依据、账户来源或规则适用性时继续查，仍不足就少交并说明；“改编”不是免除检索的理由。

## 2. 人名、邮箱和公开账户

| 内容 | 处理方式 |
|---|---|
| 个人姓名、称呼中的姓名 | `[PERSON_1]`、`[PERSON_2]`，保留必要角色，例如“采购经理 [PERSON_1]” |
| 个人登录名、账号称呼 | `[USER_1]`、`[USER_2]`；与同一主体的姓名及邮箱映射保持一致，不能把用户名原值藏到元数据 |
| 所有邮箱，包括公开机构邮箱 | `[EMAIL_1]`、`[EMAIL_2]`；From、To、CC、Reply-To、正文、签名、引用历史一并替换 |
| 企业／机构主动公开的户名、账号、开户行 | 经官方来源逐项核实后原值保留，不能改数字、遮掩成尾号、写 SYN 或把不同来源的户名和账号拼接 |
| 机构号、银行行号、统一社会信用代码 | 先确认编号体系、归属主体／网点、用途和适用时间，再保留官方原值；账号、CNAPS、SWIFT/BIC、客户号和 USCC 不可互换 |
| 私人电话、个人地址、个人证件和卡号 | 不采集来增强真实感；非必要省略，确有业务作用时使用 `[PHONE_1]`、`[ADDRESS_1]` 等类型占位符 |
| 订单、发票、合同、工单等个案标识 | 用 `[ORDER_1]`、`[INVOICE_1]`、`[CONTRACT_1]`、`[TICKET_1]`；原记录脱敏或明确改编的对象均可，不伪称生成的标识为真实原编号 |
| 邮件中的 URL、已知二维码目标 | 保留来源中实际目标及显示文字对应关系，直接作为训练输入；只处理其中的个人信息／秘密片段，不整条替换为 `[URL_n]`。原件缺目标则保持缺失；资料出处 URL 不冒充邮件目标 |
| 认证秘密、礼品卡兑换码等 | 仅描述索取／交付动作，不生成可使用的值；必要占位为 `[OTP_1]`、`[REDEMPTION_CODE_1]` |

**映射规则：**同一原始或明确改编线程、同一对照组里同一主体对应同一 token，不同主体不合并。编号按首次出现顺序分配，与标签无关。正负样本都做相同脱敏；不要仅恶意样本有 `[EMAIL_2]` 或仅正常样本保留姓名。角色名可以保留，真实个人名称及邮箱原值不要藏进 notes、答案或映射表。

**公开账户核实规则：**优先使用机构自己的公开收款页、正式公告或官方文件。记录户名、账号、开户行、可选行号的完整对应关系、来源 URL、获取日期及用途限制到 `provenance.identifiers`。所有数字作为字符串保留前导零；来源含空格的原始表示可同时保存，不能凭长度或校验算法“修正”账号。无明确公开来源就省略该项，或选择另一有来源的场景；不从姓名、地区、其他账号推算。不是每封邮件都需要出现账户。公开账号仅证明披露时的归属／用途，不证明某笔交易、资金流向、账户当前可用或付款已获授权。不能把该账号移入无关案件以补齐真实感，也不能改变账号来制造标签差异。

企业身份、合同／开票／收款主体、信用代码、账号及行号须联合核对，不能把分别真实但互不对应的字段拼成一套资料。链接原文与姓名脱敏的处理、标识的对象关系和真假声称边界见 [现实一致性](reality-contract.md)。脚本的格式、号码和引用检查不能代替归属核实。

## 3. 明确主题、来源依据与个案状态

起草前在工作笔记中明确发件人、收件人、双方关系、触发此次联系的事件，以及下列事项。笔记供理解与核对，不逐项抄成正文或增加到分类器输入。区分来源事实与 `provenance.grounding.adaptations` 中的改编设定；决定标签的状态须在输入中可见，不能只写在答案或元数据里。

1. **对象：**哪笔订单、发票、服务或账期；真实原记录和改编对象不要混为同一实际事件。
2. **已发生：**报价、下单、支付、退货、冲红或待审批；改编前后仍须自洽，不把官方规则写成具体完成状态。
3. **待处理：**缺凭证、等退款、查进度或补授权；与真实流程对应，避免为标签另造不合理障碍。
4. **当前动作：**由谁要求谁提供什么、支付什么、承认什么或授予什么权限；正常／威胁差异应对应有来源依据的流程或风险机制。
5. **结果与条件：**收件时已经知道的结果、未决事项及下一步。事后调查结论留在元数据；新安排或预期结果不能写成已经完成的事实，也不扩大为机构真实承诺。

金额和时间要对得上；改编金额须明确记录，公开账号及真实收费／税率等规则不改。内部审批或核对条件可作为合理个案设定写入输入，但不能仅凭任意新增规则就证明恶意。迟到、错填、价格争议和待确认状态不自动升级成恶意；依据不足时继续查或不收录。

进一步按 [现实关系表](reality-contract.md#1-先核对关系再核对字面) 检查主体、款项、时间版本、权限及渠道。钓鱼的虚假声称与作者写错分开：保留来源机制支持的欺骗，修复无关的流程错误；决定真实性的基准留在来源和可用上下文，不把分析写进发件人正文。

## 4. 正文长度与邮件形态

先写出完整连贯的邮件，再依据实际正文选择 `content_profile`。正式通知、首次联系、需要解释前因后果的请求可以充分展开；用户允许或要求增加篇幅时，补足同一事项的相关背景、状态变化、承接理由和后续安排。具有这些实质内容且达到下表标准时使用 `detailed`。自然成文较短时使用 `concise`，也要有该文种所需的称谓、事由和收尾。两种篇幅都可用于任一标签。

| 语言 | 当前邮件有效正文目标 | 硬性下限 |
|---|---|---|
| `zh` | 450–800 个中文字符 | 350 个中文字符 |
| `en` | 280–450 个英文单词 | 220 个英文单词 |
| `zh-en` | 450–800 个有效单位 | 350 个有效单位 |

本表仅为 `detailed` 的现有篇幅契约，不是每封邮件的起草模板或自然度评分。混合语言按“中文字符数 + 2 × 英文单词数”计算。统计排除占位符、数字串、签名、历史引用和通用套话，但正文仍须保留必要称谓和落款。仅全批明确要求详细正文时使用 `--require-detailed`。`zh-en` 要有两种语言承载意义。没有足够相关内容达到详细篇幅时，选择 `concise` 并说明与用户篇幅要求的差距。

下列信息用于补足沟通，不要求每封逐项铺开。每增加一段，都应能说明它如何帮助收件人理解或处理本次请求。采用来源事实或明确记录的合理个案改编。

1. **背景与对象：**为何现在写这封邮件，处理哪笔业务、哪个账期或哪些商品，与此前事项有何关系。
2. **本案当前状态：**已经完成、尚未完成和待确认的事项；区分资料收到、审批通过、付款发起、实际到账等不同阶段。
3. **必要的金额与凭证：**相关金额、数量、差额、文件版本及相互关系；不相关时不强塞账户或附件。
4. **具体动作和次序：**由谁处理什么，先核对什么、后提交什么，以及完成的可观察结果。
5. **本案时间与影响：**说明回复／处理时间及排期、对账或后续处理影响；改编时记录个案期限，不把工作安排升级为真实银行罚则、平台收费或无依据威胁。
6. **回复内容与异常处理：**说明需回复的信息、补件或核对条件；可以安排合理的改编角色分工，不编真实机构联系人或例外政策。

需要更多内容时，优先解释已有事实之间的关系，例如为什么此时联系、哪项变化引出了请求、回复后谁会接着处理。确需新增业务事实时回到来源核实，个案设定记录为改编。不要为达到字数增加无关凭据、客户闲谈、打印邮寄细节或同义催促。检查删除某段是否影响当前沟通；完全没有影响的支线通常应删除。

独立来信可以使用空历史和省略业务背景字段。仅在任务约定的输入范围内提供已知事实、凭证或决定；需要更多背景才能判断时，记录待核实或明确更换输入范围。忠实保留原有历史，改编历史写入 `provenance.grounding.adaptations`，不把实际系统看不到的信息当作可用上下文。

### 独立邮件与表达风格

有无历史按 [选题与形态规则](topic-selection.md) 在规划时随机选择，正文质量独立验收。独立来信使用 `history: []`，通常省略 `business_context`；收件人只读主题和当前邮件就能理解这封信在声称什么、为何联系自己、要做什么及之后会怎样。正文可自然陈述发件人的理由和声称，作者不能借此将未知的报名、授权、购买或中奖事实认定为真实。首次来信无需编造“再次提醒”“按您此前申请”等前情。

新编单封邮件默认充分构筑，不因无历史就套用三行短通知。围绕同一事项组织：有吸引力或清晰的主题 → 合适称呼与联系缘由 → 当前活动／服务状态及必要细节 → 具体请求、条件与步骤 → 相符的后续安排及服务落款。按文种自然合并与衔接，不固定段数，也不要求每封照抄此顺序。奖品内容、参与资格、补贴阶段、退税状态等细节必须贴合来源和本例，不能用泛泛的“请尽快处理”代替实质信息。

| 风格 | 如何构筑 | 避免失真 |
|---|---|---|
| 正式通知 | 主题点明通知事项，正文清楚说明适用对象、缘由、状态、需要办理的动作与反馈方式；称谓、段落和署名形成一致的机构服务口吻。 | 正式感不靠堆砌公文术语、虚构文号、官方印章或专属部门；消费者不称“财务同事”或“贵司”。通知外观不证明发件身份真实。 |
| 醒目的活动邮件 | 在有依据的活动情节中突出一个明确吸引点，如奖品、会员权益或领取资格；标题、开头和正文兑现同一信息，并自然引到参与或领取动作。可有鲜明的宣传语气。 | 不靠全篇感叹号、无依据的金额或稀缺承诺撑吸引力；不得把“有机会参与”偷换为“已经中奖”，也不把抽奖、退税、账号冻结等无关诱因拼在一起。 |

两种风格可适度结合，也都可出现于正常与威胁样本。优先写连贯且有实质内容的正文，满足详细契约时用 `detailed`；实际短系统通知、保留的短原件或用户指定简短时仍可用 `concise`，但不能以此掩盖缺失缘由、空泛请求或草率收尾。严禁用重复催促、常识性免责声明或无关业务细节凑字数。

验收时遮住元数据、历史和背景独立通读：标题承诺与正文是否一致；每段是否承接上一段；状态、时序、人称、请求与落款是否一致；收件人能否理解下一步。正文中可理解的发件人声称与足以判定真伪的证据是两回事；需要外部基准才能定性的邮件仍依原规则复核，不能为“单封可读”捏造证据。

正负对照保持相近的专业程度、长度与信息量；可在同一真实主题和已核实机制上明确改编。正常邮件无需安全宣传；威胁动作应有来源基础，不能为配对强加无依据行为。自然措辞、原有错别字或中英混用不作为标签提示。

### 分领域补足细节

- **金融：**从国内持卡人、出纳或经办人的问题写起：查哪个账期，哪笔已经扣款，回单有没有拿到，下一步找谁办。区分查账单、本人认证、修改授权和实际付款；真实手续费／费率只有原始记录或适用官方收费依据支持时才列明，不给真实银行编一个统一费率。
- **财务：**把“这次应付多少、已经付了多少、还差多少”算清楚，连上合同、发票和银行回单。票面已有不含税金额、税额和价税合计时核对三者；只知道含税总额就保留总额，不猜税率。再交代有材料依据或明确改编的复核人角色、缺票、入账及付款安排，避免只写抽象的“完成对账闭环”。
- **购物：**说清退的是哪件、留的是哪件、各自实付多少、优惠怎么分摊；商品退款和运费是否同在本次申请里分别交代。区分“快递收走了、仓库收到、已经提交退款、银行卡到账”，不要一句“处理中”贯穿整封。运费是否可退、多久到账依本例和相应来源，不自行承诺。
- **消费者活动与发放通知：**抽奖围绕邀请、结果、领取或寄送中的当前阶段展开；国补围绕具体项目的资格、立减、核销或拨付；退税围绕申报、补件、审核或退付。交代本例适用条件与当前动作，不把每封写成商家内部对账，也不混同“具备资格”“审核通过”“已经到账”。

## 5. 邮件结构与连贯性

### 从通信关系组织正文

新编的独立人工邮件默认具有下列沟通功能。可合并段落或调整次序，不套固定六段模板，也不把这些功能名写成正文小标题。

| 位置或功能 | 成文要求 |
|---|---|
| 发件人和主题 | `from` 使用能自然出现在发件栏的个人、岗位、团队或系统名称，与署名相符。匿名案例可用“客户经理”“人事部”等通用角色，个人姓名仍用 token。主题说明本次事项和目的，例如“关于借款合同期限的复核意见”，避免只罗列“两张定期和一个借款合同”。“个贷期限审核”这类流程名称不能无说明地充当人的身份。 |
| 称谓 | 根据对象使用“各位同事：”“[PERSON_1]，您好：”“财务同事：”等自然称呼。群发、单独联系和上下级关系应一致。首次联系需要的身份说明放在开头，不靠元数据让读者猜。 |
| 写信缘由与前情 | 说明为什么现在写信、承接哪次提交或哪项安排。只回顾本次请求需要的事实，避免用第三人称从头介绍整宗案件。 |
| 当前事项与衔接 | 从前情推进到现在的变化、待办或问题。连接词须对应真实的因果、转折或时间关系；增加“因此”“另外”不能修复事实之间的断裂。 |
| 请求与后续 | 明确请谁处理什么、适用条件或必要顺序、需要何种回复及之后的安排。有依据才给截止时间，状态和承诺不得越过发件人掌握的信息或声称的权限。 |
| 收尾和落款 | 收尾承接刚提出的请求，可说明等待确认或表示感谢；署名使用已出现的角色、部门或脱敏姓名。避免结尾突然转向另一套处理办法。无需每封套用“此致敬礼”。 |

第一次联系的个人来信通常需要较完整的身份和缘由。回复已有邮件时可以缩短称呼、回顾和签名，但必须承接实际存在的历史；不能为省略前情虚写“按我们之前约定”。系统提醒可以只有标题、用户称呼、简短说明、按钮与系统页脚，具体结构见 [system-notices.md](system-notices.md#2-系统通知的自然写法)。原始邮件及其节选保留原状，补写缺失称谓或落款须改列 `source-adapted`。

### 逐项检查逻辑

- **角色与知识范围。** 谁说“我”“我们”，谁是“您”“客户”，全篇保持稳定。声称代表某角色与已经得到授权分开处理；发件人不能凭空知道调查结论、受害人后续损失或未发生的动作。
- **时间与状态。** 申请、复核、批准、执行、到账各自有明确位置。未来回件不能支持今天已完成的确认，相对时间与历史时间须一致。
- **指代与对象。** 多份存单、合同、附件、金额或收件方使用稳定名称。读者应能判断“第一张”“原版本”“本次”分别指什么。
- **缘由与请求。** 说明前情如何引出此次联系，提出的动作与邮件声称的目标有关。威胁样本可以有欺骗性理由或越权请求，但需作为发件人的说法呈现；作者不替发件人证实其说法。
- **段落与收尾。** 每段推动同一沟通事项。先要求跳过复核、后又要求按复核结果办理，若无清楚的条件区分、转述或时间变化，就是写作矛盾。用于判定的“当前指令与已知基准冲突”则应保留，不能在润色时改没。
- **信息分工。** `business_context` 只放输入约定允许且收件前已知的中性基准，`history` 承载可用的先前通信。正文可自然引用它们，也不必复述整套规则。分类依据不足时核对约定范围内确实可用的信息；仍不足就进入复核，不把分析结论塞进发件人口中。

### 引用、附件与格式

- 原始主题忠实保留，改编主题与个案设定一致，不暗示未经证实的真实公告。英语主题仅在对应语言场景中采用；回复前缀与实际历史匹配。
- 人名／邮箱脱敏后保留自然称谓和署名，例如 `[PERSON_1]｜应付会计`。不得编真实机构专属职级、官方印章或员工身份来补可信度。
- 原始发件邮箱地址仍不作为当前契约的标签证据；邮箱按统一规则脱敏，原文与改编来源分别说明，不靠被抹去的发件域名或陌生显示名制造决定性差异。研究邮件头技术特征须另约输入字段。邮件正文中保留的实际 URL 属于当前可见输入，可结合请求及适用上下文审读，不能仅凭域名外观定类。
- 引用历史时逐字保持正文和脱敏 token 一致；无需每封重复整段历史。不要把两份相同历史当成新增证据。
- 日期与星期、时区、相对时间、退款阶段要一致。跨境场景写明适用市场，但不把深夜邮件本身判为恶意。
- 现有 v2 的原有或改编附件只用元数据表示，例如 `{"name":"发票_[INVOICE_1].pdf","type":"pdf"}`。仅附件名称不足以推断恶意程序或隐藏索密要求，也不能只在答案中声称附件已验真。
- 判断依赖附件可读文本时，先按 [输入范围约定](classification-quality.md#1-先固定观察范围) 明确扩展字段、来源层次与校验。现有契约下不能把摘要伪装成发件人正文或偷偷放进业务背景；原邮件本来引用的附件内容可忠实保留。
- 链接可以同时存在于两类；新记录保留实际 URL、原有按钮与附近动作说明，旧占位记录不倒推目标。未知目标和后续行为保留为缺失信息，不为判定而扩大按钮文案或提前写出网页索密步骤。
- 外加网关提示、检测结果与发件人正文分层处理；表格／HTML 转换按同一规则用于两类样本。安全通知、转发举报和引用内容按实际分类对象判断，见 [分类与复核要求](classification-quality.md#3-分离原邮件与外部裁定)。

## 6. 来源、改编与标签验收

- 核对机构、服务规则、账户、业务／风险机制的来源，并明确哪些是原记录事实、哪些是情节改编。`provenance.grounding.adaptations` 覆盖新增或调整的金额、时间、角色、对话、内部安排及请求；不能以笼统“已改编”遮住事实混淆。
- 可基于同一已核实主题、流程及风险机制制作明确标注的正常／威胁对照。最小对仅改决定性的动作或条件，共享历史、机构、账号、语气与无关细节；多处变化应如实说明。不能为平衡标签添加无来源风险或只靠任意编的审批制度制造恶意。
- Evidence 引用输入中可定位的状态与请求；标注理由说明业务关系和来源支持的风险机制，不能补输入没有的制度，或把官网账号当成本次交易授权证明。
- 盲审隐藏样本 ID、target、notes、provenance 等标注信息，保留任务允许的主题、声称身份、正文、原始链接及上下文；原始邮箱地址等当前契约不使用的特征保持脱敏。判断应由这份实际输入支持。原案被冒用的银行／企业不等于施害者；改编邮件不代表真实组织曾发送、认可或实施对应行为。
- 正常材料允许催办、更正、退款、密码管理、争议和合理差错；恶意不能只由急迫语气、品牌、占位符或一次错误决定。缺少所需流程／风险依据时继续检索，仍不足就少交并说明。
- 逐条做两遍审读。第一遍只看邮件及其必要历史，检查称谓、缘由、请求、后续及落款是否完整自然，是否存在角色漂移、指代不明、因果断裂和收尾冲突，并完成 [用词与渠道检查](#面向收件人的用词与渠道检查)，不能只检查有没有称呼和落款。第二遍对照 `target` 与来源核对可见证据和事实边界。任一遍不通过就修订并重查受影响的引用。
- 新编独立人工邮件遗漏称谓、来意或落款，正文像第三人称案例说明，段落加入无关支线，或前后请求相互抵消，都需要返修。系统通知、已有往来和真实节选按其实际文种判断。脚本不以“您好”“谢谢”等关键词代替语义验收。
- 批量生成时两类标签都采用同样的专业程度与邮件完整度；按收件关系、业务阶段和渠道变化表达。检查反复出现的开场、段落顺序、无关细节和结尾，避免只替换机构名称形成模板化语料。
- 混合任务需另检验正常难例、业务差错与信息不足项。按 [分类验收](classification-quality.md#6-把要求落实为验收) 独立审读、核对对照及分组，不能把正文流畅或结构校验通过宣称为检测效果。
- 旧 `assets`／已有语料仅作历史结构参考，不是新事实证据；无检索依据或未披露改编的旧样本不能直接沿用为新记录。检查时报告冲突；仅优化 Skill 不授权重写原样本、金额、账号或来源。

## 7. 既有失败样本的回归检查

用户提供的“两张定期和一个借款合同”用于检查邮件写作质量，所述业务规则未经本节核验，不直接作为新语料的事实来源。

这类样本须先明确是经办人向复核同事写信，还是其他关系，再选合适称呼和署名。正文应围绕此次期限处理，从相关前情自然过渡到当前请求。保留到期顺序、原期限与当前改录要求的对应关系；自动续存咨询、装修报价、铅笔标记、邮寄地址和分类打印，只有确实影响此次请求时才保留。

原文先要求不记录复核退回，后又要求下一经办查清真实到期依据，需检查两者是否存在清楚的条件或阶段区分。修订作者误写的矛盾时，保留原来的威胁动作及支持判断的事实。仅在原文前后加“您好”和“谢谢”仍不能通过本节验收。

**邮件回复用词回归。** 用户指出“结果我再在这个线程回你”不是自然的中文邮件表达。改为“有处理结果后，我会回复这封邮件告知你”。同段“原工单由班长用共享邮箱接续即可”可改为“原工单可由班长使用共享邮箱继续处理”。这些仅为措辞示例，不是独立训练记录或新的事实来源。

验收时同时保留该片段的语义：账号被限制发送，但仍可登录和查看来件；原工单由班长通过共享邮箱继续处理；个人邮箱的解封申请已受理，结果尚待回复。不能改成账号全面不可用、解封已批准、工单已办结或新增审批权限；本节不证明任何具体产品具有这些限制或授权规则。相反，若邮件实际讨论“工作线程阻塞”，应保留技术含义，不把所有“线程”替换为“邮件”。
