# 真实感、数据处理与核对规范

规划和核对时阅读，写作阶段不加载。本页规定以下内容：
- 地区与金额。
- 脱敏和公开账户。
- 个案事实的一致性。
- 盲审之后规划者的核对项。

本页不规定邮件该怎么写：写法由写作者按 [写作简报](writing-brief.md) 自行判断，由 [盲审](blind-review.md) 检验。

相关文档：[来源与改编指引](source-grounding.md) · [场景指引](scenario-playbook.md) · [系统通知](system-notices.md)

## 默认地区、金额和语气

以中国大陆收件场景为主，默认写中文邮件、人民币金额。美元需要有跨境采购、出口收款、境外服务续费或其他有依据的美元外币业务背景。境内美元业务仍按境内处理。外币和业务地区依实际依据填写。

地区和币种放进元数据：`business_region: CN`；`transaction_scope` 区分 `domestic` 与 `cross_border`；`currencies` 只列本例实际涉及的 `CNY`／`USD`。跨境例用 `cross_border_context` 说明中国一方是谁、与哪里发生什么交易及所用币种；境内美元例保持 `domestic`，另用 `currency_context` 交代真实适用的外币业务和使用美元的原因。两种情况都要在正文给读者足够的业务背景，不能只靠元数据补理由。代码用于元数据，正文写“32,480元”“169.50元”“2,450美元”，不要写成代码在前、数字在后的财务接口格式。

上述金额仅示意格式，不是可借用的个案事实。正文可自然说明应付、已付和剩余金额。引用真实记录时保持原金额、币种和精度；改编金额时在 `provenance.grounding.adaptations` 明确记录并保证算术一致，不能说成来源原值。不要虚构真实汇率、擅自把美元换算成人民币或将两种币种直接相加。公开账户的户名、账号、开户行及行号是原始资料，绝不能随金额排版一起改写、去空格或截断。

### `register` 字段

`register` 记录关系和文种。写作完成后按实际邮件填写，不作为写作要求。

| `register` | 适用的关系和文种 |
|---|---|
| `daily_business` | 同事、熟悉的供应商和日常跟进 |
| `customer_service` | 品牌或商家对个人消费者、客服对客户、首次联系外部对象 |
| `formal_notice` | 正式通知、合同函件和系统自动通知 |

真实原件保留原有语气，不能为了统一风格而虚构官方身份或改变原材料的性质。正式语气不能证明官方身份、政策或权威。

### 面向收件人的用词与渠道检查

盲审之后，核对新编主题、正文和改编历史是否使用收件人实际会说的邮件语言。`thread`、`history`、上下文、样本、标签等生成或数据组织概念，不应因作者看过字段定义就进入普通业务正文。谈邮件沟通时不使用“在这个线程回你”“本线程继续跟进”“拉入邮件线程”，按真实动作写“回复这封邮件”“通过邮件告知你”“抄送相关同事”等；保持原有收件范围和回复关系，不能在改词时擅自增加抄送人或改走其他渠道。

| 检查项 | 容易失真的表达或关系 | 成文处理 |
|---|---|---|
| 邮件、聊天与工单 | 把邮件叫“线程／会话”，把工单处理写成“在邮件里关闭”，或无聊天背景却说“私信我” | 区分沟通渠道和业务对象：回复邮件、在工单中更新、通过已有聊天渠道联系；只有已知操作渠道才写具体入口 |
| 动作及对象 | “接续工单”“回传结果”“推进闭环”等说法掩盖实际动作 | 按意思写“继续处理原工单”“通过邮件告知处理结果”“核对完成后更新工单状态”等；这些是可选表达，不是逐词替换表，不能补出原文没有的动作或承诺 |
| 称谓及人称 | 同一收件人无缘由地切换“你／您”，把同事称“贵司”，或直接对客户写“请客户提供” | 按真实关系统一称谓，明确“我／我们／您／对方”指谁；角色名和敬语自然搭配，不用过度公文化表达代替清楚说明 |
| 状态的准确程度 | 将“已受理”写成“已批准”，把“限制发送”扩大为“无法登录”，把“已提交付款”写成“已经到账” | 保留已知状态、限制范围和未决结果；不为显得正式而改变完成程度、权限或业务含义 |
| 回复与通知方式 | 一面要求“回复本邮件”，一面写“系统自动发送，请勿回复”；或变更渠道却仍称“在这里回复” | 当前要求与实际可用回复方式一致；自动通知引用其他邮件的回复要求时保留清楚层次，不能凭空补一个客服入口解决矛盾 |
| 引用与附件 | 没有明确对象却写“上面那个／如下附件／见历史”，新增“再次提醒”却无相应前情 | 在允许输入内准确指向此前邮件、附件名称或本次事项；已有对象就说明，缺少对象就删去无依据的承接，不编造历史或附件 |

这些检查适用于新编主题、正文、签名及改编历史，也适用于两类标签。发现问题时，把具体问题转告写作者重写，然后核对事实、请求、收件关系和 evidence 的精确引用是否仍然一致。

不用全局禁词或机械替换：讨论 CPU 线程、数据库回写、网络链路或真实产品“会话视图”时保留准确术语；英文邮件的自然 `email thread` 用法、内部 `thread_family_id` 和真实原文引用也不受中文业务措辞规则误伤。`redacted-source` 原文不能无声明地润色；修改措辞须按已有契约归为 `source-adapted`。自动结构校验不证明这项语义审读已经完成。

## 1. 真实依据与情节改编

- 按指定主题先明确要让收件人识别的动作，再实际检索支持这一动作的威胁机制和必要的正常流程。分别记录真实机构、适用规则、原案事实和新邮件改编。
- 允许基于上述依据改编交易金额、个案时间、业务阶段、角色分工、对话及内部复核安排；逐项记入 `provenance.grounding.adaptations`，不把新情节说成真实往来或来源事实。该许可不包含凭空设计真实品牌活动，或改变已核实活动的奖品、资格、规则与适用期次。内部安排只作为本例明确设定，不冒称真实银行、平台或公司的现行制度。
- 具名机构、企业户名、账号、开户行、支行、机构／银行代码及公开政策必须真实且可核实，不随情节改写。覆盖正文、历史、签名和附件；不得编真实机构专属部门、员工身份或政策以补可信度。不需指向现实的收件方、经办企业等可声明为 `[ORG_n]` 虚构机构，见 [真人感渲染](persona-rendering.md#3-render-声明)。
- 上述核实针对现实实体和制度断言。用户原件中未核实的服务显示文字可作为发件人声称保留并记录其未知状态，不为它编造机构来源，也不把它列成已验证实体。生成时可使用通用系统角色，不能冒称一个未核实的产品真实存在。
- 来源匿名的案例不能替换成另一个真实公司并宣称还原；公开账户不能补进无关原案。独立改编使用真实机构时，另核业务和账户用途，并在元数据说明新情节，不能暗示该机构真实涉案或实施恶意行为。
- 官方帮助可支持服务规则，反诈说明可支持风险机制，案件通报支持其明示的事件；均不自动证明某封新邮件真实发出。可据此明确改编，但不能声称改写的是未公开的邮件原文，或由 App 功能推断机构存在某种官方邮件流程。
- 分别记录发布日期、事件日期、访问日期和改编时间，不把无日期旧文的“近期”解释成当前真实案件。缺乏业务／风险依据、账户来源或规则适用性时继续查，仍不足就少交并说明；“改编”不是免除检索的理由。

## 2. 人名、邮箱和公开账户

| 内容 | 处理方式 |
|---|---|
| 个人姓名、称呼中的姓名 | `[PERSON_1]`；称呼和签名用 `[SURNAME_1]总`、`[GIVEN_1]`、`[SIGNATURE_1]`。人物的机构、部门和职位在 `render.people` 声明，渲染时换成虚构姓名 |
| 个人登录名、账号称呼 | `[USER_1]`、`[USER_2]`；与同一主体的姓名及邮箱映射保持一致，不能把用户名原值藏到元数据 |
| 所有邮箱，包括公开机构邮箱 | `[EMAIL_1]`、`[EMAIL_2]`；From、To、CC、Reply-To、正文、签名、引用历史一并替换。在 `render.mailboxes` 声明归属和地址类型（本机构、免费邮箱、仿冒、外部、原件实际域名），渲染时生成对应地址 |
| 企业／机构主动公开的户名、账号、开户行 | 经官方来源逐项核实后原值保留，不能改数字、遮掩成尾号、写 SYN 或把不同来源的户名和账号拼接 |
| 机构号、银行行号、统一社会信用代码 | 先确认编号体系、归属主体／网点、用途和适用时间，再保留官方原值；账号、CNAPS、SWIFT/BIC、客户号和 USCC 不可互换 |
| 私人电话、个人地址、个人证件和卡号 | 不采集来增强真实感；非必要省略，确有业务作用时使用 `[PHONE_1]`、`[ADDRESS_1]` 等类型占位符，渲染为虚构的分机、座机或地址 |
| 订单、发票、合同、工单等个案标识 | 用 `[ORDER_1]`、`[INVOICE_1]`、`[CONTRACT_1]`、`[TICKET_1]`；原记录脱敏或明确改编的对象均可，渲染时生成真实格式的虚构编号，不伪称为真实原编号 |
| 邮件中的 URL、已知二维码目标 | 保留来源中实际目标及显示文字对应关系，直接作为训练输入；只处理其中的个人信息／秘密片段，不整条替换为 `[URL_n]`。原件缺目标则保持缺失；资料出处 URL 不冒充邮件目标 |
| 认证秘密、礼品卡兑换码等 | 仅描述索取／交付动作，不生成可使用的值；必要占位为 `[OTP_1]`、`[REDEMPTION_CODE_1]` |

**映射规则：**同一原始或明确改编线程、同一对照组里同一主体对应同一 token，不同主体不合并。渲染器按 `thread_family_id` 为同一 token 生成同一人物，两类标签使用同一规则，不读取标签。编号按首次出现顺序分配，与标签无关。正负样本都做相同脱敏；不要仅恶意样本有 `[EMAIL_2]` 或仅正常样本保留姓名。角色名可以保留，真实个人名称及邮箱原值不要藏进 notes、答案或映射表。

**公开账户核实规则：**优先使用机构自己的公开收款页、正式公告或官方文件。记录户名、账号、开户行、可选行号的完整对应关系、来源 URL、获取日期及用途限制到 `provenance.identifiers`。所有数字作为字符串保留前导零；来源含空格的原始表示可同时保存，不能凭长度或校验算法“修正”账号。无明确公开来源就省略该项，或选择另一有来源的场景；不从姓名、地区、其他账号推算。不是每封邮件都需要出现账户。公开账号仅证明披露时的归属／用途，不证明某笔交易、资金流向、账户当前可用或付款已获授权。不能把该账号移入无关案件以补齐真实感，也不能改变账号来制造标签差异。

企业身份、合同／开票／收款主体、信用代码、账号及行号须联合核对，不能把分别真实但互不对应的字段拼成一套资料。链接原文与姓名脱敏的处理、标识的对象关系和真假声称边界见 [现实一致性](reality-contract.md)。脚本的格式、号码和引用检查不能代替归属核实。

## 3. 明确主题、来源依据与个案状态

规划时明确发件人、收件人、双方关系、触发这次联系的事件以及下列事项，写进 [情境卡](writing-brief.md#2-情境卡)，不加到分类器输入里。区分来源事实与 `provenance.grounding.adaptations` 中的改编设定；决定标签的状态须在输入中可见，不能只写在答案或元数据里。

1. **对象：**哪笔订单、发票、服务或账期；真实原记录和改编对象不要混为同一实际事件。
2. **已发生：**报价、下单、支付、退货、冲红或待审批；改编前后仍须自洽，不把官方规则写成具体完成状态。
3. **待处理：**缺凭证、等退款、查进度或补授权；与真实流程对应，避免为标签另造不合理障碍。
4. **当前动作：**由谁要求谁提供什么、支付什么、承认什么或授予什么权限；正常／威胁差异应对应有来源依据的流程或风险机制。
5. **结果与条件：**收件时已经知道的结果、未决事项及下一步。事后调查结论留在元数据；新安排或预期结果不能写成已经完成的事实，也不扩大为机构真实承诺。

金额和时间要对得上；改编金额须明确记录，公开账号及真实收费／税率等规则不改。内部审批或核对条件可作为合理个案设定写入输入，但不能仅凭任意新增规则就证明恶意。迟到、错填、价格争议和待确认状态不自动升级成恶意；依据不足时继续查或不收录。

进一步按 [现实关系表](reality-contract.md#1-先核对关系再核对字面) 检查主体、款项、时间版本、权限及渠道。钓鱼的虚假声称与作者写错分开：保留来源机制支持的欺骗，修复无关的流程错误；决定真实性的基准留在来源和可用上下文，不把分析写进发件人正文。

## 4. 篇幅与邮件形态

篇幅不设目标。写作者按人物和处境决定写多长，盲审读者检验是否合适：
- 读者能指出收件人用不着的内容，就删掉。
- 读者复述不出请求或缘由，就补上，但只补收件人需要知道的部分。

正式通知、手机上的两句回复、醒目的活动邮件，都可以出现在两类标签中。

`content_profile` 可以省略。用户明确要求详细正文时，才在情境卡中写明篇幅要求，并把记录标为 `detailed`，用 `--require-detailed` 校验：
- 当前邮件的有效正文至少 350 个中文字符（`zh`）、220 个英文单词（`en`），或 350 个混合单位（`zh-en`，中文字符数加两倍英文单词数）。
- 统计时排除占位符、数字串、签名、历史引用和常见套话。
- 没有足够的相关内容时不凑字数，在报告中说明差距。

### 独立邮件

有无历史按 [选题与形态规则](topic-selection.md) 在规划时随机选择。独立来信使用 `history: []`，通常省略 `business_context`；收件人只读主题和当前邮件，就要能明白这封信想让自己做什么（盲审的第一问）。规划时注意：

- **不写不存在的前情。** 首次来信没有前情，情境卡里不写“此前申请”“再次提醒”。
- **声称不等于事实。** 发件人对报名、授权、购买或中奖的说法只是声称，不能借此把未知的事实当作已证实。
- **活动和通知不夸大、不拼凑。** 活动邮件不得把“有机会参与”写成“已经中奖”，也不把抽奖、退税、账号冻结等无关诱因拼进同一封。真实机构的通知不配虚构的文号、印章或专属部门。
- **证据不足时换形态。** 需要外部基准才能定性的邮件，选择往来或含业务背景的形态，或进入复核；不能为了单封可判定而编造证据。

正负对照保持相近的信息量。正常邮件不需要安全宣传，威胁动作要有来源依据。错别字、口语和中英混用由画像决定，不是标签提示。

### 规划时把情境写具体

情境卡里的事实越具体，写作者越能写出真实的邮件。按领域确认这些事实：

- **金融：** 持卡人、出纳或经办人要处理的具体问题，例如哪个账期、哪笔已经扣款、回单是否拿到、下一步找谁。分清查账单、本人认证、修改授权和实际付款。真实的手续费或费率，只有原始记录或适用的官方收费依据支持时才写进情境卡。
- **财务：** 算清应付、已付和差额，并关联合同、发票和银行回单。票面有不含税金额、税额和价税合计时，三者要一致；只知道含税总额就只给总额，不猜税率。复核人、缺票、入账和付款安排要有材料依据，或明确记为改编。
- **购物：** 退的是哪件、留的是哪件、各自实付多少、优惠怎么分摊，商品退款和运费是否在同一次申请里。确定当前处于快递揽收、仓库签收、已提交退款还是已到账。运费是否可退、多久到账，按本例和相应来源确定，不自行承诺。
- **消费者活动与发放通知：** 抽奖要确定处于邀请、结果、领取还是寄送阶段；国补要确定具体项目的资格、立减、核销或拨付；退税要确定处于申报、补件、审核还是退付。分清“具备资格”“审核通过”和“已经到账”。

## 5. 连贯性与格式核对

盲审之后，规划者按下列项目核对。发现问题时把具体问题转告写作者重写，不把这些检查项交给写作者。

### 逐项检查逻辑

- **角色与知识范围。** 谁说“我”“我们”，谁是“您”“客户”，全篇保持稳定。声称代表某角色与已经得到授权分开处理；发件人不能凭空知道调查结论、受害人后续损失或未发生的动作。
- **时间与状态。** 申请、复核、批准、执行、到账各自有明确位置。未来回件不能支持今天已完成的确认，相对时间与历史时间须一致。
- **指代与对象。** 多份存单、合同、附件、金额或收件方使用稳定名称。读者应能判断“第一张”“原版本”“本次”分别指什么。
- **缘由与请求。** 说明前情如何引出此次联系，提出的动作与邮件声称的目标有关。威胁样本可以有欺骗性理由或越权请求，但需作为发件人的说法呈现；作者不替发件人证实其说法。
- **段落与收尾。** 每段推动同一沟通事项。先要求跳过复核、后又要求按复核结果办理，若无清楚的条件区分、转述或时间变化，就是写作矛盾。用于判定的“当前指令与已知基准冲突”则应保留，不能在润色时改没。
- **信息分工。** `business_context` 只放输入约定允许且收件前已知的中性基准，`history` 承载可用的先前通信。正文可自然引用它们，也不必复述整套规则。分类依据不足时核对约定范围内确实可用的信息；仍不足就进入复核，不把分析结论塞进发件人口中。

### 引用、附件与格式

- `from` 是 `{name, address}`：人工邮件的 `name` 用 `[PERSON_n]`；团队或系统用实际会出现在发件栏的名称；`address` 用已声明的 `[EMAIL_n]`，并与署名相符。不把岗位或流程名称拼接成发件人。
- 原始邮件及其节选保留原状；补写缺失的称谓或落款，要改登记为 `source-adapted`。
- 原始主题忠实保留，改编主题与个案设定一致，不暗示未经证实的真实公告。英语主题仅在对应语言场景中采用；回复前缀与实际历史匹配。
- 称谓和署名用 `[SURNAME_1]经理`、`[SIGNATURE_1]`，职位和部门在 `render.people` 声明。虚构机构可以有部门、职位和签名；真实机构不得编造专属职级、官方印章或员工身份来补可信度，冒充者的自称按发件人声称处理。
- 发件地址关系在 `render.mailboxes` 中如实声明，渲染后对检测器可见。它只作辅助，不能单独决定标签，每种关系在两类中都要出现。Received、认证结果等其他邮件头技术特征须另约输入字段。邮件正文中保留的实际 URL 属于当前可见输入，可结合请求及适用上下文审读，不能仅凭域名外观定类。
- 引用历史时逐字保持正文和脱敏 token 一致；无需每封重复整段历史。不要把两份相同历史当成新增证据。
- 日期与星期、时区、相对时间、退款阶段要一致。跨境场景写明适用市场，但不把深夜邮件本身判为恶意。
- 现有 v2 的原有或改编附件只用元数据表示，例如 `{"name":"发票_[INVOICE_1].pdf","type":"pdf"}`。仅附件名称不足以推断恶意程序或隐藏索密要求，也不能只在答案中声称附件已验真。
- 判断依赖附件可读文本时，先按 [输入范围约定](classification-quality.md#1-先固定观察范围) 明确扩展字段、来源层次与校验。现有契约下不能把摘要伪装成发件人正文或偷偷放进业务背景；原邮件本来引用的附件内容可忠实保留。
- 链接可以同时存在于两类；新记录保留实际 URL、原有按钮与附近动作说明，旧占位记录不倒推目标。未知目标和后续行为保留为缺失信息，不为判定而扩大按钮文案或提前写出网页索密步骤。
- 外加网关提示、检测结果与发件人正文分层处理；表格／HTML 转换按同一规则用于两类样本。安全通知、转发举报和引用内容按实际分类对象判断，见 [分类与复核要求](classification-quality.md#3-分离原邮件与外部裁定)。

## 6. 来源、改编与标签验收

- 核对机构、服务规则、账户、业务／风险机制的来源，并明确哪些是原记录事实、哪些是情节改编。`provenance.grounding.adaptations` 覆盖新增或调整的金额、时间、角色、对话、内部安排及请求；不能以笼统“已改编”遮住事实混淆。
- 可基于同一已核实主题、流程及风险机制制作明确标注的正常／威胁对照。最小对仅改决定性的动作或条件，共享历史、机构、账号、语气与无关细节；多处变化应如实说明。不能为平衡标签添加无来源风险或只靠任意编的审批制度制造恶意。
- Evidence 引用输入中可定位的状态与请求；标注理由说明业务关系和来源支持的风险机制，不能补输入没有的制度，或把官网账号当成本次交易授权证明。
- 盲审只给读者渲染后的输入，不给样本 ID、`target`、notes 和 `provenance`。判断应由这份实际输入支持。原案被冒用的银行／企业不等于施害者；改编邮件不代表真实组织曾发送、认可或实施对应行为。
- 正常材料允许催办、更正、退款、密码管理、争议和合理差错；恶意不能只由急迫语气、品牌、占位符或一次错误决定。缺少所需流程／风险依据时继续检索，仍不足就少交并说明。
- 先完成 [盲审](blind-review.md)，再做本节核对。读者的复述、真人感和标签判断是语义验收的主要依据；本节核对来源、改编、证据和对照。脚本不以“您好”“谢谢”等关键词代替语义验收。
- 检查同一批邮件中反复出现的开场、段落顺序、长度和结尾。出现雷同时，分开上下文重写，不要只替换机构名称。
- 混合任务需另检验正常难例、业务差错与信息不足项。按 [分类验收](classification-quality.md#6-把要求落实为验收) 独立审读、核对对照及分组，不能把正文流畅或结构校验通过宣称为检测效果。
- 旧 `assets`／已有语料仅作历史结构参考，不是新事实证据；无检索依据或未披露改编的旧样本不能直接沿用为新记录。检查时报告冲突；仅优化 Skill 不授权重写原样本、金额、账号或来源。

## 7. 既有失败样本的回归检查

用户提供的“两张定期和一个借款合同”用于检查邮件写作质量，所述业务规则未经本节核验，不直接作为新语料的事实来源。

这类样本须先明确是经办人向复核同事写信，还是其他关系，再选合适称呼和署名。正文应围绕此次期限处理，从相关前情自然过渡到当前请求。保留到期顺序、原期限与当前改录要求的对应关系；自动续存咨询、装修报价、铅笔标记、邮寄地址和分类打印，只有确实影响此次请求时才保留。

原文先要求不记录复核退回，后又要求下一经办查清真实到期依据，需检查两者是否存在清楚的条件或阶段区分。修订作者误写的矛盾时，保留原来的威胁动作及支持判断的事实。仅在原文前后加“您好”和“谢谢”仍不能通过本节验收。

**自证式写法回归。** 现有语料中 REC-004872（骗子向受害人解释“您自己没有发起也能收到确认”）、SYN-REC-634（“供方明确的新日期不要报上去”）和 REC-004969（先说明盒饭没有送到，再要求扣掉餐补）都由正文自证恶意。这类问题由盲审的第 4 问发现，见 [盲审](blind-review.md)。维护 Skill 时不改写这些记录，只用于检查新文档和新批次。

**邮件回复用词回归。** 用户指出“结果我再在这个线程回你”不是自然的中文邮件表达。改为“有处理结果后，我会回复这封邮件告知你”。同段“原工单由班长用共享邮箱接续即可”可改为“原工单可由班长使用共享邮箱继续处理”。这些仅为措辞示例，不是独立训练记录或新的事实来源。

验收时同时保留该片段的语义：账号被限制发送，但仍可登录和查看来件；原工单由班长通过共享邮箱继续处理；个人邮箱的解封申请已受理，结果尚待回复。不能改成账号全面不可用、解封已批准、工单已办结或新增审批权限；本节不证明任何具体产品具有这些限制或授权规则。相反，若邮件实际讨论“工作线程阻塞”，应保留技术含义，不把所有“线程”替换为“邮件”。
