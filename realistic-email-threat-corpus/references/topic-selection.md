# 全场景随机选题与邮件形态

每次生成或续写前使用本页。随机性用于选择题材、收件关系和可成立的邮件形态；来源与可见证据决定情节能否验收。仅维护 Skill 时不生成训练记录。

## 1. 从全部适用场景建立候选池

用户本轮限定领域、主题、收件对象、标签或输入范围时，在该范围内随机。未限定时，候选池来自 [场景指引](scenario-playbook.md)、[系统通知](system-notices.md) 和 [BPC 流程篡改场景](bpc-scenarios.md) 的全部适用场景，覆盖金融、财务、购物、职场及个人服务通知，不能沿用上次挑出的少数主题作为完整候选池。同一场景在多页被引用只算一个候选，避免新增入口让相同情节重复加权。

国补发放、退税、抽奖是重点场景：增加其可用子场景的丰富度，并给予合理优先权重。重点不等于每批必选，更不等于只在这三类之间轮换；其余适用场景始终保留非零抽中机会。

| 重点 | 可独立取材的关系与阶段 |
|---|---|
| 国补发放 | 个人消费者的资格领取、订单优惠、补件、核销或款项状态，以及有依据的商家申报、审核和业务流程变更；按具体政策区别立减与拨付，不一律写成给个人打款 |
| 退税 | 个人纳税人的申报、补件、账户核对和退税状态，也可按任务范围覆盖单位经办或企业事项；不强加雇主或财务背景 |
| 抽奖 | 品牌、平台或商家对个人消费者的活动邀请、抽奖参与、中奖通知、领奖和寄送，也保留员工活动；小米、华为只是品牌例子，不构成固定名单 |

[有奖问卷](survey-and-mail-inspection.md#1-问卷与礼品场景)与其他场景一并随机抽选。来源确为抽奖的问卷可归入抽奖重点；答完即得参与奖励、礼品转寄通知、健康调查邀请按各自的机制取材。平台检查不完整属于观察条件，不能作为活动本身或邮件标签来抽样。

良性批次和混合批次中的正常样本同样从全池随机抽题，并纳入 [日常良性邮件](feedback-and-benign.md#4-日常良性邮件)（会议、交接、报价、营销、订阅、自动回复等）。用户提供的真实误报不参与随机抽题，按条围绕其触发特征衍生良性邮件。

候选项至少区分领域、具体主题、收件关系、当前阶段和主要请求。品牌、金额或产品名称不同，但关系、步骤与诱导方式相同的邮件，仍属于同一类近重复情节。不要靠改 `scenario_type` 后缀伪造多样性。

来源条目是取材入口，不是封闭题库。先从全池随机抽取检索方向，再实际搜索、阅读并从有依据的真实活动／流程／风险机制中确定本批情节；同主题检索到多个适用对象时继续随机选取。可纳入 Skill 范围内新发现的有依据场景。未核实候选只能安排检索，不能直接成文；不能随机拼接品牌、活动名称、奖品和日期来创造“真实活动”。来源约束见 [source-grounding.md](source-grounding.md)。

## 2. 实际执行随机选择

1. **读取已有覆盖。** 续写时检查已有语料的领域、主题、收件关系、来源／活动和近期重复。已有批次记录可复用；没有既有数据就从完整候选池开始，不虚构历史分布。
2. **建立可选层次。** 按领域分层，再按具体主题组织候选。把同一事件或模板的近重复变体合并计数，避免某类仅因可列出更多品牌而占据全部概率。
3. **调用随机数生成器。** 在执行环境中实际使用例如 Python `random.SystemRandom()` 的随机选择；不靠模型顺手挑选并称为随机，也不只打乱成品顺序。默认不固定种子；用户需要复现时使用并报告指定或新生成的种子，保留当次候选池与权重依据。
4. **跨领域分层抽样。** 未限定领域、独立抽样单元数量允许且来源充分时，每批覆盖多个领域；先随机选择本轮领域及顺序，再在领域内随机抽取具体主题。小批次不必塞进所有领域，单条或单个配对任务从全部适用领域抽取；后续批次继续纳入此前未抽中的领域。
5. **兼顾重点与新颖度。** 主题抽样使用正权重；一种可用起点是 `重点系数 / (1 + 近期同类数量 + 本批同类数量)`，重点系数可设为 2、其余为 1。按批次规模调整并说明，不能把它解释为真实收件箱比例。近期过多的主题降低权重而非永久移除；不要直接选择最高权重代替随机抽样。
6. **减少批内重复。** 在同层候选内优先无放回抽取，确需复用时再开始新一轮，重新随机化并选择不同的有依据关系、阶段或机制。不得固定按金融→财务→购物→工作或国补→退税→抽奖依次生成。

抽中题材后实际调用搜索引擎并打开资料，保留查询、日期、来源和支持范围，形成有依据的提纲后才能写正文；抽样计划本身不证明活动真实。依据不足时继续查证，仍不足则从剩余适用候选中重新随机选择，或报告范围内缺口；不能因为取材方便就整批退回一个熟悉领域。用户限定的题材不能擅自换到范围外。

## 3. 有无历史同样在规划阶段随机

先按任务范围和来源筛选能成立的形态，再随机选取。独立单封与有往来的邮件都属于正常生成形态，不以标签决定是否提供历史。

| 形态 | 输入与写作要求 |
|---|---|
| 单封、无上下文 | `history: []`，省略 `business_context`。只凭当前邮件构成完整通信，适用于首次收到的品牌活动、中奖、退税或补贴通知等有依据场景；不假设收件人有未提供的往来。威胁样本须在骗子不自证的前提下仍能凭请求本身判定，否则改选有往来或含背景的形态 |
| 有先前邮件 | `history` 仅放当前时点可用且有作用的往来；轮数由沟通需要决定，不固定为 2–4 轮，不为填数组补虚构回复 |
| 有实际可用背景 | 仅在约定允许时提供中性的 `business_context`，历史仍可为空；有背景与有历史是两件事，不能把背景字段当作默认必填项 |

对两种以上形态都成立的候选，调用随机数生成器选择，并在批次内兼顾尚未覆盖的形态。用户要求单封或现有检测器只接收当前邮件时，直接采用单封形态，在该范围内随机题材，不为随机性扩大输入范围。

人工邮件的发件人画像卡（正式程度、篇幅、设备、称呼和书写习惯）也用随机数生成器抽取，与标签无关，记入 `render.style`，见 [画像卡](writing-brief.md#3-画像卡)。

随机发生在构思和选材时，不能从已成文记录中随机删除决定性历史。如果判断需要此前的审批、付款或活动规则，保留约定可用的证据，或另选可独立成立的题材；不能把隐含历史偷偷写入答案、把后续调查塞入正文，或强行将证据不足标为恶意。

单封邮件只凭主题和正文就要让收件人明白发件人想要什么；写多长、怎么组织，由写作者按人物和处境判断，由 [盲审](blind-review.md) 检验。含“此前”“再次”“按约定”等表述时，在当前邮件内清楚交代所指事项，或承接约定可用的前情；发件人声称曾购买或参与活动不等于已获证实，也不因此强制添加历史。

保留原件时不随机删改原有历史。已有输入契约优先；跨境／美元记录要求业务背景等限制见 [schema.md](schema.md)，不能为抽中“无上下文”而丢弃必填事实。当前信息不足时按 [classification-quality.md](classification-quality.md) 复核。

## 4. 配对、复核与交付

- 以完整配对为抽样单位。配对两侧使用相同的历史、业务背景及约定输入范围，不分别随机有无历史；独立记录不强制配对。
- 成文后检查分布是否仍集中于一个领域、同一场景或固定模板，检查无历史是否只对应某个标签。发现集中时调整下一轮选材，不能仅换品牌或打乱记录顺序。
- 简要报告实际覆盖的领域、重点主题、单封／有历史／含背景数量、正常样本中误报衍生与日常邮件的数量、各发件地址类型在两类中的分布及取材缺口；上述形态存在交集时说明统计口径。仅在使用可复现种子时报告该种子。抽样说明和统计留在批次报告，不加入分类器 `input`，也不新增必填记录字段。
- 随机抽中不代表已通过来源、语义或结构验收。正式数量仍按已验收记录计数；待核实项另行处理，不用它们充数。
