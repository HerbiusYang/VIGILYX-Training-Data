# 写作简报：情境卡、画像卡与写作

规划完成后，用本页把查实的情境交给写作者。写作者以发件人的身份写信，篇幅、结构、语气和措辞都由它按人物和处境自己判断。本页只规定交给写作者什么、不交什么。它不提供范文，也不规定邮件该怎么写。

## 1. 为什么这样交接

- **规则会被抄进邮件。** 规则一旦进入写作上下文，就会被原样写进邮件，例如“区分申请与到账”“基准与偏离”。
- **字数目标会逼出填充。** 为了凑够字数，写作者会加无关的段落。
- **范文会导致雷同。** 有了范文，一批邮件会写得一模一样。

真人写信时，脑子里只有一个具体的人和一件具体的事。写作者需要的也就是这些。

## 2. 情境卡

用第二人称、自然语言写给写作者，包含以下内容：

| 项目 | 内容 |
|---|---|
| 你是谁 | 用占位符写的身份，例如 `[ORG_1]` 的生产计划主管 `[PERSON_1]`；和收件人的关系；与这件事有关的个人处境，比如忙不忙、在哪里、急不急 |
| 写给谁 | 收件人和抄送人；他们对这件事已经知道多少 |
| 发生了什么 | 来源查实的事实和已记录的改编设定，只写到发件人此刻知道的程度；之后才发生的事和调查结论都不写 |
| 你想要什么 | 希望对方现在做什么 |
| 你心里的打算 | 只用于诱导和恶意邮件：发件人的真实目的，以及他不会说出口的部分。正常邮件写“没有别的打算” |
| 之前的往来 | 已有邮件的原文；这封是不是回复 |
| 不能改的事实 | 真实机构名、公开账户、活动规则、链接原值等；写作者照用，不得改动或补造 |
| 可用的占位符 | 人物 `[PERSON_n]`，称呼可用 `[SURNAME_n]`、`[GIVEN_n]`；签名 `[SIGNATURE_n]`；机构 `[ORG_n]`、`[ORGSHORT_n]`；域名 `[DOMAIN_n]`、`[LOOKALIKE_n]`；编号 `[ORDER_n]`、`[INVOICE_n]`、`[CONTRACT_n]`、`[TICKET_n]` 等；链接路径 `[SLUG_n]`。需要人名、编号或链接时用这些占位符，不编造真实值 |
| 时间 | 本批生成当年的具体发信日期、时间和时区。涉及往期账单或上年度税款时，另写明业务所属期间 |

情境卡里不写以下内容：
- 标签，以及“正常”“恶意”“诱导”这类字样。
- 证据、“基准”“偏离”等分析用语，以及需要体现的风险点清单。
- 措辞或句子示例。
- 字数要求。只有用户明确要求详细正文时，才写一句篇幅要求，例如“这封信要把来龙去脉讲清楚”。

“你心里的打算”只在卡片里，读者看不到。如果判定需要原审批、原账户、考勤或供餐记录等基准，就把它放进往来邮件或业务背景，不能指望写作者在正文里透露。

诱导和恶意邮件的关键在“你心里的打算”。写作者知道发件人在骗人，就会像骗子那样写：给出合理的理由，只提出自己需要的请求，不解释自己的意图。所以不必再告诉它“不要自证”。同样，正常邮件只给处境，不提醒它“要写得正常”。

## 3. 画像卡

用随机数生成器抽取画像卡，抽取方式与 [随机选题](topic-selection.md#2-实际执行随机选择) 相同。画像与标签无关，记入 `render.style`；设备同时写入 `render.people` 的 `device`。

| 维度 | 取值（可以扩展） |
|---|---|
| 年龄与经历 | 刚入职、做了多年的老员工、管理者、个体经营者、退休人员 |
| 正式程度 | 随意、日常、正式 |
| 写信习惯 | 话少只说结论、习惯交代来龙去脉、爱用编号列表、一句一段 |
| 设备 | 电脑、手机 |
| 打字习惯 | 标点随意、偶尔有错别字、中英夹杂、语气词多、几乎不用语气词 |
| 此刻状态 | 很忙、着急、从容、不太情愿 |

画像卡只描述一个人，不规定写法。这样的人会怎么写这封信，由写作者自己决定。系统通知和营销邮件的“画像”是发信方的产品与模板：服务类型、品牌风格、是否用 HTML 卡片。

## 4. 交给写作者

- **用独立上下文执行。** 用子代理或新会话写作，只传入情境卡、画像卡和下面这段提示。不传规则文档、来源原文、其他邮件或已有语料。如果开不了子代理，规划者写完卡片后就不再翻看规则，只依据卡片写。
- **写作提示**（这是给写作者的指令，不是范文）：

  > 你就是情境卡里的人，画像卡描述了你的习惯。现在写这封你此刻真的会发出的邮件。写什么、写多长、怎么称呼、要不要分段，都按你的身份和处境决定。人名、机构、编号和链接用卡片给出的占位符。只返回主题和正文。

- **往来邮件逐封写。** 每封由各自的发件人按各自的卡片写，按时间顺序进行，后一封能看到前一封的原文。
- **系统通知和营销邮件也以发信方身份写。** 发信方可以是通知系统、商家运营或诈骗团伙。
- **不要在一个上下文里连续写很多封。** 需要批量时分开写，避免后写的模仿先写的。

## 5. 改写

- **把读者的反馈原样转告。** 盲审读者指出的问题，例如“看不出你想让对方做什么”“第三段收件人用不着”，原样转告写作者，不附规则。
- **情境本身有问题时回到规划。** 如果是事实不清、请求不成立，或证据不在可见范围内，先修改情境卡再重写。
- **改写后重新盲审。**

## 6. 写作结果进入记录

- **规划者负责登记。** 把主题和正文填入 `input`，补上 `from`、`to`、`sent_at`，按 [schema.md](schema.md) 登记来源与改编。情境卡中的设定记入 `grounding.adaptations`。
- **写作者自由添加的细节也是改编。** 写作者可能补上时间、数量、闲聊等细节，这些都属于改编。如果涉及真实机构的规则、费用或账户，要回到来源核实，否则删除。
