# 现实一致性：业务、链接与身份标识

生成前用本节核对设定，成文后核对输入。真实感来自可成立的业务关系和通信过程；邮件措辞可以基于来源改编，现实实体、公开标识和业务规则不能凭“看起来像”补造。与 [来源改编](source-grounding.md)、[分类验收](classification-quality.md) 配合使用。

## 1. 先核对关系，再核对字面

| 核查对象 | 必须对应的关系 | 不足时如何处理 |
|---|---|---|
| 对公账户 | 户名 ↔ 账号 ↔ 开户银行／支行 ↔ 公开用途；涉及行号时还须对应同一网点或有依据的清算关系 | 不拼接甲公司户名、乙公司账号和另一支行行号；缺项不推算，也不要求所有邮件强行列全收款资料 |
| 行号和机构代码 | 按来源注明 CNAPS、SWIFT/BIC 或其他实际体系，区分开户行、代理／清算行和银行内部编号 | 不用总行代码代替支行代码，不把 SWIFT 当国内支付系统行号；相同地区或银行品牌不能证明对应关系 |
| 统一社会信用代码 | 代码 ↔ 登记主体全称；区分母公司、子公司和分支机构，历史名称按来源期间处理 | 使用 `institution_code` 与 `code_system: USCC`；不得从名称、地区或校验算法生成一个“真实代码” |
| 合同、发票与收款 | 合同方、销售／服务方、开票方、收款方是否一致；不一致是否存在本案已知的代理收款或授权依据 | 不自动把不同主体判恶意，也不默认为同一集团即可代收；缺少决定性授权事实则待核实 |
| 货物与服务权益 | 订单／工单 ↔ 商品或服务 ↔ 退件／交付地点 ↔ 实际领取人 ↔ 本人或经办授权 | 区分买方、寄件人、承运人、服务点和代领人；主体不同可有合法委托，新地址和第三方代收不单独定性 |
| 履约与状态记录 | 实际收货、争议解决、验收、核销或赔付事实 ↔ 记录状态 ↔ 后续放款或权利变化 | 不把申请当批准、登记当交付、核赔当到账；是否允许部分验收、补赔或转赠按具体规则核实 |
| 结算基数与授信 | 合格交易、退款／取消、结算期、扣减项、可用额度和实际放货权限彼此对应 | 不假设每个返利计划同样扣减，不将跨期更正当造假；真实企业或有效额度不证明具体订单和操作人获授权 |
| 金额与进度 | 应付、已付、退款、余额及币种可相互核对；申请、审核、提交支付与实际到账分开 | 具体税率、手续费和到账承诺须有适用来源；没有依据不增加，不把待办写成已完成 |
| 时间与版本 | 邮件发送、订单、附件版本、审批、截止时间前后相容；节日福利、活动、补贴按对应年度／期次 | 不把过期活动当当前规则；只有年月日时不随意补星期、工作日或节假日断言 |
| 角色与权限 | 发件人与收件关系、岗位可知信息及可请求动作一致；称谓、人称、签名、历史中角色连续 | 人事、财务、IT、平台商家和政府机构不能互换权限；首次联系不能假定未交代的熟悉关系 |
| 链接、附件和沟通渠道 | 按钮实际指向、附件名称／类型、正文提及的文件版本与当时可见材料一致 | 没有附件正文、跳转链或网页内容时不能补造；真实跨渠道案件改为邮件须声明改编及适用边界 |

代码长度、字符集和校验位只能帮助发现录入错误，不证明机构存在、标识归属、账户当前可用或本次交易获授权。适用编码规范与公开查询入口见 [实体资料](public-entity-sources.md#统一社会信用代码与行号的核验入口)。当前脚本检查声明结构和精确引用，不能完成这些业务核验。

真实诈骗邮件可能包含虚假身份、政策或授权说法。分别保留“发件人声称”与“来源证实的现实事实”：前者是有风险机制依据的改编内容，记录在 `grounding.adaptations`；后者才进入事实映射。不能将发件人的谎称变成 Skill 的真实政策断言，或把无关真实企业／公开账户标为已证实涉案。真实标识值仍不得改造。

## 2. 链接保留原文，个人信息分开处理

- **新邮件保留有来源的实际 URL。** 协议、主机、端口、路径、查询参数、片段和编码保持来源原貌，不因标签改变格式，不一律换成占位符、保留域或文字“点击链接”。裸域、短链、长查询串、IP 主机或国际化域名仅在来源确有时保留，不为了显得可疑而随机构造。已知二维码目标作为目标文本保留，无须生成可扫描图片。
- **保留显示与目标的对应。** 原文为 Markdown／HTML 时保留可读正文中的链接关系，不执行 HTML／脚本；只有可见按钮和另行给出的目标时，可在 `body` 用忠实的 Markdown 链接表示并记 `format_adaptation`。不得为不存在的按钮补地址，或用安全通报／新闻报道 URL 代替邮件里的目标。不要新建未定义的 `links` 字段来暗中输入额外信息。
- **姓名仍脱敏。** 称呼、签名、历史和引用中的个人姓名统一使用 `[PERSON_n]`；邮箱、个人登录名沿用 `[EMAIL_n]`、`[USER_n]`。如果这些个人信息嵌在 URL 中，只替换相应片段，并在改编／处理记录说明；域名、其他路径与参数结构尽量保留。密码、会话令牌、一次性认证值同样不能原值入库。记录替换位置和原因，不在映射表或答案中留原值。来源中只有脱敏链接时不尝试还原，应披露覆盖缺口。
- **链接依据和当前状态分开。** 对报道披露的钓鱼目标，在来源元数据记录报道时间、具体位置和所支持的历史用途；不要声称目标现在仍然恶意、在线或受同一人控制。保留 URL 不要求打开可疑目标，校验程序不访问链接、提交表单或解析远程重定向；使用已公开的可信报告核实来源即可。
- **旧记录保持兼容。** 默认校验允许历史 `[URL_n]`；新批次加 `--require-raw-urls` 防止沿用整条 URL 占位。无链接的 BEC、普通回复或原件缺失按钮目标均可存在；开关通过不证明链接真实或每条应有链接。

保留链接后，仍按检测器的真实输入判断：外观正常、HTTPS、短链、复杂参数、站外地址、显示文字与目标不同，都不单独决定标签。公开报道中的事后分析不能偷偷写进当前邮件。URL 中的长数字也可能是资源或追踪标识；根据来源判定其含义，不为通过号码扫描随意改写，明确的个人信息仍需按片段处理。

## 3. 钓鱼逼真度与正常对照共同验收

1. **一个可理解的联系缘由。** 收件人为什么会收到、与现有工作／账户／活动有什么关系、此时为什么需要处理，要能衔接。短系统通知由服务与状态交代，不强塞长故事。
2. **一个主要请求与合理阶段。** 保留真实机制中的第一步或当前步骤；通知引流、回复收集、授权请求、附件交付、付款变更分别按所处阶段写，不将所有威胁堆在一封邮件里，不把后续网页索密搬进初始通知。
3. **像发件人实际在沟通。** 正文不夹分类理由、风险清单或旁白。不得为了让标签明显而固定加入“不要核验”“不要留痕”，也不让正常邮件固定背诵安全口号。攻击者的欺骗说法可以存在，但作者造成的角色漂移、无关支线、日期错误和收尾抵消必须修正。
4. **样式覆盖两类。** 人工正式往来、简短回复、系统卡片、通知表格和合法共享服务都可以出现在两类中；中英文、敬语、落款、链接数量、篇幅和紧迫程度不与标签绑定。混合批次也纳入普通会议／材料交接／进度确认等日常正常邮件，不只用高度警觉的安全提醒作正常对照。
5. **检查可见证据与缺口。** 引用实际请求及所需基准；缺证据可待核实，不能修改事实强行凑正负配对。抽检分别报告写作／业务不一致、来源不足、信息缺失、标签分歧，未训练评估时不声称提高了检测率。
6. **避免记住链接和机构。** 批次审查来源事件、模板、相同目标 URL、机构／账户与标签的集中度；相关活动及其变体按关联分组后划分数据集。共享平台根域本身不自动把所有无关业务合成一组。使用原始链接的评估另报已见目标和未见目标覆盖，不能把记住某批域名当作理解了钓鱼行为。

这些要求用于完善 Skill 和后续生成验收，不授权发送邮件、部署页面或开展实际投递。仅维护 Skill 时不生成或改写训练集。
